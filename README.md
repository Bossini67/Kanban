# Kanban Board

A small Kanban board backed by Supabase Postgres, a FastAPI API, and a React +
TypeScript frontend.

## 1. Create the Supabase table

In your Supabase project, open **SQL Editor**, create a query, and run the contents
of [`schema.sql`](./schema.sql):

```sql
create table if not exists public.cards (
    id bigint generated by default as identity primary key,
    title text not null,
    status text not null default 'todo'
        check (status in ('todo', 'doing', 'done')),
    created_at timestamptz not null default now()
);

alter table public.cards enable row level security;

grant select, insert, update, delete on public.cards to anon;
grant usage, select on sequence public.cards_id_seq to anon;

drop policy if exists cards_public_select on public.cards;
create policy cards_public_select on public.cards for select to anon using (true);

drop policy if exists cards_public_insert on public.cards;
create policy cards_public_insert on public.cards for insert to anon with check (true);

drop policy if exists cards_public_update on public.cards;
create policy cards_public_update on public.cards for update to anon
    using (true) with check (true);

drop policy if exists cards_public_delete on public.cards;
create policy cards_public_delete on public.cards for delete to anon using (true);
```

This board has no user sign-in. These policies deliberately let anyone with the
board API URL read, add, move, and delete cards. Only use this setup for a board
whose contents are okay to make public; authentication and per-user access are not
implemented.

## Supabase URL and API key

1. Sign in at <https://supabase.com/dashboard> and open your project. If you do
   not have a project yet, create one and wait for it to finish provisioning.
2. In the project dashboard, open **Project Settings → API** (the API keys page
   may be labeled **API Keys**).
3. Copy the **Project URL**. It looks like
   `https://abcdefghijk.supabase.co`. This is `SUPABASE_URL`.
4. Copy the **Publishable key** (often labeled `anon` on older projects). This is
   `SUPABASE_KEY`. It may start with `sb_publishable_` or look like a long JWT.
   It is designed for client/API use with the database access controlled by the
   policies above.
5. Do **not** use or share the **Secret key** (`sb_secret_...`) or legacy
   `service_role` key. Those bypass row-level security and must never be put in
   frontend configuration, chat, or source control.

Paste the real values into `backend\.env`, replacing the two example values:

```dotenv
SUPABASE_URL=https://your-project-ref.supabase.co
SUPABASE_KEY=your-publishable-or-anon-key
ALLOWED_ORIGINS=http://localhost:5173
```

Keep `backend\.env` on your computer and private. The file is ignored by Git.
After saving it, start the backend using the command below. If you already ran
only the original `CREATE TABLE` statement, rerun the full updated `schema.sql`
in the Supabase SQL Editor to add the required grants and policies.

## 2. Run the backend locally

From the repository root, create and activate a virtual environment:

```powershell
python -m venv backend\venv
backend\venv\Scripts\python.exe -m pip install -r backend\requirements.txt
Copy-Item backend\.env.example backend\.env
notepad backend\.env
```

In Notepad, replace the example values for `SUPABASE_URL` and `SUPABASE_KEY` with
the Project URL and Publishable/anon key from the steps above, then save the file.
Keep this file private and do not commit it. `ALLOWED_ORIGINS` defaults to
`http://localhost:5173`; it can be a comma-separated list of origins.

Start the API:

```powershell
backend\venv\Scripts\python.exe -m uvicorn main:app --app-dir backend --reload
```

The API is available at <http://localhost:8000>; interactive API docs are at
<http://localhost:8000/docs>.

## 3. Test the backend

Leave the API running in its PowerShell window. Open a second PowerShell window
in the repository root and run these commands one at a time:

```powershell
$card = Invoke-RestMethod -Method Post -Uri http://localhost:8000/cards `
  -ContentType "application/json" -Body '{"title":"First task"}'
$card
Invoke-RestMethod -Method Get -Uri http://localhost:8000/cards
Invoke-RestMethod -Method Patch -Uri "http://localhost:8000/cards/$($card.id)" `
  -ContentType "application/json" -Body '{"status":"doing"}'
Invoke-RestMethod -Method Get -Uri http://localhost:8000/cards
Invoke-RestMethod -Method Delete -Uri "http://localhost:8000/cards/$($card.id)"
Invoke-RestMethod -Method Get -Uri http://localhost:8000/cards
```

You should see the new card in the first GET, its status changed to `doing` in the
second GET, and the card absent from the final GET. A successful DELETE has no
response body. PATCH rejects statuses other than `todo`, `doing`, or `done`;
requests for an unknown card return `404`.

## 4. Run the frontend locally

Install Node.js 20.19+ or 22.12+ first. Make sure the backend is running as
described above. In a second PowerShell window, from the repository root, run:

```powershell
Copy-Item frontend\.env.example frontend\.env
Set-Location frontend
npm install
npm run dev
```

Open the local URL printed by Vite, normally <http://localhost:5173>. The frontend
reads its API URL from `VITE_API_URL`; the example points to
`http://localhost:8000`. The backend's default `ALLOWED_ORIGINS` already allows
that local frontend origin.

Add a task using Enter or **Add task**, move it using the status dropdown, and
delete it using the × button on the task. If the board shows a connection error,
check that the API is running and that `frontend\.env` points to its URL.

## Deployment

### Backend: Google Cloud Run

1. Ensure the Supabase schema above has been run.
2. From the repository root, build and deploy the backend image (replace
   `PROJECT_ID` and choose a region):

   ```powershell
   gcloud builds submit --tag gcr.io/PROJECT_ID/kanban-api backend
   gcloud run deploy kanban-api `
     --image gcr.io/PROJECT_ID/kanban-api `
     --platform managed `
     --region REGION `
     --allow-unauthenticated `
     --set-env-vars "SUPABASE_URL=https://your-project.supabase.co,SUPABASE_KEY=your-key,ALLOWED_ORIGINS=http://localhost:5173"
   ```

3. For a production frontend, set `ALLOWED_ORIGINS` to its exact HTTPS origin
   (for example, `https://your-project.pages.dev`) rather than leaving only the
   localhost origin. Set `SUPABASE_URL` and `SUPABASE_KEY` as Cloud Run environment
   variables; never add credentials to the image or source control. For production,
   prefer storing the Supabase key in Secret Manager and exposing it to Cloud Run
   as a secret environment variable.
4. Copy the Cloud Run service URL for the frontend's API base URL.

Cloud Run supplies `PORT`; the container listens on that port.

### Frontend: Cloudflare Pages

1. Push the project to a Git provider supported by Cloudflare Pages and create a
   Pages project from that repository.
2. Set the root directory to `frontend`.
3. Set the build command to `npm run build` and the build output directory to
   `dist`.
4. Add the `VITE_API_URL` environment variable for both production and preview
   builds. Set it to the deployed Cloud Run service URL, without a trailing slash.
   Set `NODE_VERSION` to `24`. Vite embeds the API URL in the frontend bundle
   during the build.
5. Deploy the Pages project. Copy its site origin, such as
   `https://your-project.pages.dev`, and set Cloud Run's `ALLOWED_ORIGINS` to that
   exact origin. Redeploy or update the Cloud Run service after changing it.

### Deploy both apps to Vercel

The GitHub repository contains two apps, so create **two Vercel projects** from the
same repository. Vercel supports FastAPI through its Python runtime and supports
monorepos by setting a different root directory for each project.

#### 1. Deploy the backend

1. In the [Vercel dashboard](https://vercel.com/dashboard), select **Add New →
   Project**, then import `Bossini67/Kanban`.
2. Set **Root Directory** to `backend`. Vercel should detect FastAPI from
   `requirements.txt` and `main.py`; leave the detected framework/build settings
   at their defaults.
3. Add these project environment variables for **Production**:
   - `SUPABASE_URL`: your Supabase project URL.
   - `SUPABASE_KEY`: your Supabase publishable (or legacy `anon`) key. Do not use
     the Supabase secret or `service_role` key.
   - `ALLOWED_ORIGINS`: `http://localhost:5173` for the initial deployment.
4. Deploy the project. Copy its Vercel URL, for example
   `https://kanban-api-your-team.vercel.app`.
5. Check that `https://YOUR-BACKEND-URL.vercel.app/docs` opens. The Supabase
   schema and public policies from `schema.sql` must already be applied.

#### 2. Deploy the frontend

1. From the Vercel dashboard, select **Add New → Project** and import
   `Bossini67/Kanban` again as a separate project.
2. Set **Root Directory** to `frontend`. Use the detected Vite settings, or set
   the build command to `npm run build` and output directory to `dist`.
3. Add the `VITE_API_URL` environment variable for **Production**, set to the
   backend Vercel URL from the previous section, without a trailing slash.
4. Deploy and copy the frontend's production URL.

#### 3. Allow the frontend to call the backend

1. Open the **backend** Vercel project settings and set `ALLOWED_ORIGINS` to the
   frontend's exact production origin, for example
   `https://kanban-your-team.vercel.app` (no trailing slash).
2. Redeploy the backend so the setting takes effect.
3. Refresh the frontend. To use Vercel preview deployments, add their exact
   origins to `ALLOWED_ORIGINS` as a comma-separated list, then redeploy the
   backend.

Changing a Vercel environment variable requires a new deployment. Keep Supabase
credentials in Vercel environment settings, never in GitHub or frontend
environment variables. Since this app has no user sign-in, the policies in
`schema.sql` allow public read/write access to the board; only use it for data
that is okay to make public.

For details, see Vercel's guides for [FastAPI deployments](https://vercel.com/docs/frameworks/backend/fastapi)
and [monorepos](https://vercel.com/docs/monorepos).
